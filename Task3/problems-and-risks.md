# InsureTech: проблемы и риски текущей архитектуры при росте нагрузки

Контекст: сервисы core-app и ins-comp-settlement получают продукты и тарифы синхронным REST-запросом к ins-product-aggregator, который в момент вызова сам опрашивает все страховые компании (сейчас 5, скоро 10). Дополнительно ins-comp-settlement раз в сутки забирает из core-app по REST все страховки, оформленные за день.

## 1. Взаимодействие core-app / ins-comp-settlement -> ins-product-aggregator

| N | Проблема / риск | Последствия при росте |
| --- | --- | --- |
| 1.1 | Синхронная цепочка: время ответа ins-product-aggregator = время ответа самой медленной страховой компании + агрегация. | С ростом числа СК с 5 до 10 растет вероятность, что хотя бы одна СК ответит медленно или с ошибкой. Запрос core-app упирается в таймаут, локальная реплика тарифов не обновляется. |
| 1.2 | Нет собственного хранилища у ins-product-aggregator: каждый вызов - это заново N запросов во внешние API. | Нагрузка на API СК растет пропорционально числу потребителей и частоте опроса. Возможна блокировка со стороны СК по их rate limit. |
| 1.3 | Сбой одной СК ломает весь ответ (агрегат возвращается в рамках одного запроса). | Ошибка одной СК блокирует обновление тарифов всех СК. Нужна частичная деградация. |
| 1.4 | Pull-модель с фиксированным интервалом (core-app - раз в 15 минут, ins-comp-settlement - раз в сутки). | Данные устаревают до 15 минут (у settlement - до суток). Клиент может увидеть неактуальный тариф, оформление по нему приводит к расхождениям и ручным разборам. При этом большая часть запросов холостая - тарифы меняются редко. |
| 1.5 | Пиковая нагрузка "пачкой": все экземпляры core-app (после масштабирования через HPA их больше) одновременно делают полный запрос раз в 15 минут. | Рост числа реплик core-app кратно увеличивает нагрузку на ins-product-aggregator и на СК (эффект thundering herd). |
| 1.6 | Каждый потребитель держит свою копию тарифов, обновляемую разными способами и в разное время. | Расхождение данных о продуктах между core-app и ins-comp-settlement. Ошибки во взаиморасчетах. |
| 1.7 | Нет механизма повторной доставки: если ночной запрос settlement упал, данные за сутки не обновятся до следующей ночи. | Ошибки в реестре на выплату агентских премий. |
| 1.8 | Добавление новой СК или нового потребителя требует изменений в нескольких сервисах. | Высокая связность, медленное подключение 5 новых СК. |

## 2. Взаимодействие ins-comp-settlement -> core-app (оформленные страховки)

| N | Проблема / риск | Последствия при росте |
| --- | --- | --- |
| 2.1 | Раз в сутки выгружаются все страховки за день одним REST-запросом. | Объем ответа растет вместе с продажами (рекламная кампания). Долгий тяжелый запрос, таймауты, нагрузка на core-db в момент выгрузки. |
| 2.2 | Нагрузка на core-app и core-db ложится на тот же монолит, который обслуживает клиентов. | При круглосуточной работе на все часовые пояса "ночного окна" больше нет - выгрузка совпадает с пиком у клиентов из других регионов. |
| 2.3 | Нет гарантии полноты: при сбое во время выгрузки часть страховок может быть потеряна или выгружена дважды. | Ошибки в расчете агентских премий, финансовые потери и споры со СК. |
| 2.4 | Данные о страховках в settlement отстают до 24 часов. | Невозможно строить отчетность и сверку ближе к реальному времени. |
| 2.5 | Временная связность: если core-app недоступен в момент запроса, settlement не получит данные. | Ручной перезапуск, риск сорвать ежемесячный срок отправки реестра. |

## 3. Общие архитектурные риски

| N | Проблема / риск | Последствия при росте |
| --- | --- | --- |
| 3.1 | Отсутствуют паттерны отказоустойчивости на интеграциях (Timeout, Retry, Circuit Breaker). | Каскадные отказы: медленная СК -> занятые потоки ins-product-aggregator -> таймауты core-app -> отказ сайта. |
| 3.2 | Одна общая БД PostgreSQL (разные схемы) на одной ВМ. | Тяжелые выгрузки одного сервиса влияют на остальные. Единая точка отказа. |
| 3.3 | Нет атомарности "запись в БД + уведомление других сервисов". | При переходе на события без Transactional Outbox возможна потеря события или отправка события о несохраненной записи (dual write). |
| 3.4 | Нет наблюдаемости по интеграциям. | О проблемах узнаем от пользователей (см. проблему 3 бизнеса). |
| 3.5 | Нет управления контрактами событий: формат сообщений между сервисами нигде не зафиксирован и не версионируется. | При переходе на события и подключении новых СК и потребителей любое изменение формата (переименование или удаление поля) ломает потребителей, которые обновляются не одновременно с продюсером. |

## 4. Предлагаемые решения (отражены на диаграмме контейнеров)

1. **Event-Streaming для продуктов и тарифов.** ins-product-aggregator получает собственную БД (ins-product-aggregator-db) и по расписанию опрашивает каждую СК независимо (отдельный поток на СК - Bulkhead, Timeout, Retry, Circuit Breaker). Изменение продукта или тарифа сохраняется в БД и публикуется событием `ProductTariffChanged` в топик Kafka `insurance.products.tariffs` (ключ - id продукта, compacted-топик хранит последнее состояние каждого продукта). core-app и ins-comp-settlement подписаны на топик (каждый своей consumer group) и обновляют локальные реплики (Event-Carried State Transfer). Синхронный REST от потребителей к агрегатору больше не нужен. Отказ одной СК не мешает обновлению остальных. Новый потребитель подключается подпиской, новая СК - только настройкой в агрегаторе.
2. **Event-Streaming для оформленных страховок.** core-app при оформлении страховки публикует событие `PolicyIssued` в топик `insurance.policies.issued`. ins-comp-settlement потребляет события в течение дня и накапливает реестр в своей БД. Суточная REST-выгрузка из core-app убирается. Ежемесячный реестр формируется из локальной БД settlement без нагрузки на core-app.
3. **Transactional Outbox.** Используется в core-app и в ins-product-aggregator: бизнес-запись и запись события в таблицу outbox выполняются в одной транзакции. Отдельный relay (Debezium через Kafka Connect, CDC по WAL PostgreSQL) читает outbox и публикует события в Kafka. Это исключает потерю событий и dual write. Гарантия доставки - at-least-once, поэтому потребители идемпотентны (дедупликация по eventId / версии продукта).
4. **Контракты событий.** Схемы событий (Avro) хранятся в Schema Registry, режим совместимости BACKWARD: продюсер может только добавлять необязательные поля, несовместимое изменение отклоняется при публикации схемы. Потребители обновляются независимо от продюсера.
5. **Надежная доставка.** Kafka (3 брокера, replication factor 3, min.insync.replicas=2). Для ошибок обработки - retry-топики и DLQ. Lag потребителей и DLQ мониторятся с алертами.
6. **Синхронные взаимодействия, которые остаются:** web -> core-app, core-app -> client-info, web -> client-info, оплата. Они нужны в рамках пользовательского запроса, декомпозиция функциональности между сервисами не меняется.
